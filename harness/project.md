# Project instructions

Project-owned. Add instructions specific to this repository here, such as operational cautions, domain rules or verification notes that do not fit a spec, ADR or rule file. harness-lab creates this file once and never replaces your edits; keep `AGENTS.md`, `CLAUDE.md` and `harness/workflow.md` identical to the template so `harness-lab update` can refresh them.

- Require both same-provider independent review and cross-provider review for meaningful code changes: Claude-authored changes receive a separate Claude review and a Codex review; Codex-authored changes receive a separate Codex review and a Claude review. Claude is the primary development tool, but the same rule applies in either direction.
- Start the reviewer in a separate session or agent context using `harness-review` (or Claude's generated `code-reviewer` agent). Give it the review target, base commit, relevant specs/acceptance criteria, and verification results. Review the actual changes, including uncommitted changes when applicable, with read-only instructions.
- The development session coordinates both reviews: use a separate native agent for same-provider review and invoke the other provider's non-interactive CLI from the repository (`codex exec` from Claude, `claude -p` from Codex). These are separate reviewer contexts; pass the review inputs explicitly rather than assuming conversation history is shared. Review-only invocations must not recursively request further reviews or start implementation. Use read-only permissions where supported, and do not bypass permission checks.
- The author addresses findings; Critical and High fixes must be reviewed again by the reviewer that raised them, or explicitly justified in the delivery report. Both reviews must cover the final changes before claiming review completion. The author remains responsible for integration and verification.
- Track both review results separately. Neither review substitutes for the other. If either reviewer cannot be run, report that review as pending and provide the review handoff; do not claim it was completed. Trivial changes such as typos, comments, docs or one-line configuration edits may skip review with a stated reason.
